# Hermes 与 OpenClaw 产品对比：同是开源 Agent，两条完全不同的路

> 上一篇《Hermes 底层核心机制剖析》是把源码拆开看机制；这一篇换个镜头：不比代码，比产品定位和生态打法，把 Hermes 和另一个很热的开源 agent 框架 OpenClaw 放到同一张台面上。

动手之前先交代两条声明，免得这篇被当成测评读：

- Hermes 侧的机制描述，以《机制剖析》的源码分析为准；OpenClaw 侧的说法来自产品级公开资料与两家文案，我没有对 OpenClaw 做过源码级核查，具体实现以对方官方文档为准。
- 文中的 Star 数、Skill 数都是文案所注时间点（2026-04 前后）的快照。聚合站上 OpenClaw 的 star 从 10 万到 34.7 万的说法都有，这种数字没法核实，当量级印象看看就好，别引用成事实。

## 一、Hermes 这个项目本身

Hermes Agent 是 Nous Research 于 2026 年 2 月正式开源的自主 AI 智能体框架。基本信息：

| 维度 | 详情 |
|---|---|
| 出品方 | Nous Research（美国开源 AI 研究实验室） |
| 开源协议 | MIT（完全免费，可商用） |
| 技术栈 | Python（占比 93.6%） |
| 支持系统 | Linux、macOS、Windows（通过 WSL2） |
| GitHub Stars | 17,000+（2026 年 4 月） |

核心定位就是官方标语那一句："the agent that grows with you"（与你共同成长的 AI）。它想换个学法：不靠用户手动配置技能，让 Agent 在运行中自己生成、优化、存储技能代码。《机制剖析》第 6 节拆过的复盘管线和 Curator，就是这句标语在源码层的样子。

## 二、本质差异：深度进化 vs 协同作战

| 对比维度 | Hermes Agent | OpenClaw |
|---|---|---|
| 核心设计 | 单一智能体深度进化 | 多智能体协同作战 |
| 记忆机制 | 分层记忆架构 | 短期记忆为主，持久化较弱 |
| 技能系统 | 自动生成并迭代 Skill | 预设 Skill + 社区生态 |
| 部署方式 | 自托管，数据本地存储 | 云端 + 本地混合 |
| 学习闭环 | 内置闭环学习系统 | 依赖外部训练 |
| 交互模式 | 长期陪伴型数字员工 | 任务驱动型执行工具 |

## 三、架构设计

| 维度 | Hermes Agent | OpenClaw |
|---|---|---|
| 架构模式 | 单体深度进化 | 多体协同作战 |
| 核心目标 | 长期陪伴，越用越懂 | 任务执行，高效完成 |
| 扩展方式 | 垂直深化（技能积累） | 水平扩展（Agent 数量） |
| 状态管理 | 强状态持久化 | 弱状态，任务级隔离 |
| 容错策略 | 学习失败，积累经验 | 快速重试，切换 Agent |

一个拟人化的读法：Hermes 像一位长期合作的私人助理，它记住你的喜好和习惯，每次任务做完还会自己复盘、沉淀技能、调整做法，服务方式确实会"越用越顺"。支撑这一点的是"可写运行时"：运行中就能生成和修改技能文件。而 OpenClaw 像一支特种部队，针对每个任务组队、干完解散；人格、规则、Skill 都由用户设定和安装，技能的构建、记忆的整理压缩都要人来参与，更像一套高度可编排的工具集合。

两者没有高下，只有取舍：前者的能力强弱取决于"任务经验的质量"，后者取决于"社区与配置的质量"。

## 四、记忆机制

| 特性 | Hermes Agent | OpenClaw |
|---|---|---|
| 记忆分层 | 核心 / 画像 / 技能 / 长期（四层表述） | 短期 / 长期（两层） |
| 存储介质 | SQLite + 文件系统 | 内存 + 向量数据库 |
| 检索方式 | FTS5 全文检索 + 语义匹配 | 向量相似度检索 |
| 持久化能力 | 跨会话强持久化 | 会话级持久化 |
| 记忆容量 | 文件 + 数据库，无向量库瓶颈 | 受向量数据库限制 |
| 隐私保护 | 本地存储，数据不出本机 | 依赖云端服务 |

产品文案把这说成 Hermes 的分层记忆解决了 OpenClaw 的"失忆"问题。按那份文案的说法，后者有三个局限：多轮复杂任务里早期上下文容易被截断；存的是嵌入向量，难以直接阅读和编辑；检索靠相似度匹配，可能漏掉关键信息。反过来，Hermes 用结构化 Markdown 文件存记忆，人能直接打开看、动手改，也就是所谓"可解释记忆"。

这里要对个表。《机制剖析》从源码里看到的是"三类记忆"（程序性 / 陈述性 / 会话历史），两家宣传口径里的"四层"（核心 / 画像 / 技能 / 长期）是按存储层和加载策略重新切了一刀，说的其实是同一套东西：画像 ↔ `user` store，陈述 ↔ `memory` store，程序 ↔ 技能，长期 ↔ session_search。想核对机制，去看《机制剖析》第 5 节，别信表格广告。

## 五、技能系统

| 特性 | Hermes Agent | OpenClaw |
|---|---|---|
| 技能来源 | 自动生成 + 手动编写 | 社区生态 + 预设模板 |
| 技能格式 | Markdown（可读可编辑） | JSON/YAML（结构化） |
| 技能进化 | 自动迭代优化 | 依赖社区更新 |
| 技能共享 | 导出 Markdown 文件 | 通过技能市场分发 |
| 技能触发 | 语义匹配 + 条件判断 | 关键词匹配 + 路由 |

两边各一个典型场景。Hermes：做完一次复杂数据分析，它自己提炼出"数据分析报告生成"技能，下次同类任务直接复用。背后是 use_count/patch_count 记账加 Curator 生命周期那套管线。OpenClaw：技能靠开发者手写，或从社区下载现成的，胜在生态大（文案注：50+ 消息平台集成、13,000+ 社区 Skill）。

生态广度上 OpenClaw 领先，这没什么不好承认。但两边技能的来源方向是反的：OpenClaw 是"外部注入"，写好了装进来；Hermes 是"内部生长"，干着干着自己长出来。"可写运行时"加复盘管线，就是"内部生长"四个字的实底。

## 六、什么场景选谁

**选 Hermes 的场景**：

1. 需要长期陪伴型 AI 助手（个人知识管理、习惯养成）；
2. 重视数据隐私（本地部署，数据不出本机）；
3. 任务类型相对固定，可通过技能积累持续提升效率；
4. 偏好简洁交互（单一 Agent，无需管理多 Agent 协作）。

**选 OpenClaw 的场景**：

1. 需要处理复杂多变任务（多 Agent 协同，动态组队）；
2. 重视执行效率（并行处理，快速完成）；
3. 需要丰富生态（社区技能即拿即用）；
4. 团队协作场景（多角色分工，流程自动化）。

一句诚实的旁注：上面这组"单一 Agent vs 多 Agent"的对比说的是产品主叙事的侧重，不是能力有无。按《机制剖析》第 7 节的拆解，Hermes 的 delegate 委派、Cron、Kanban 编排都搭在内核之上。我自己的博客流水线（微信发一个主题，kanban 上五个角色接力写稿）恰好就落在两者叙事的交叠区。

## 七、小结

OpenClaw 是一个让用户"养"出来的 AI 执行平台，价值在连接一切、灵活编排；Hermes 是一个会自己"长大"的 AI 成长搭档，价值在越用越懂你、越用越聪明。两者不是替代关系，各占一边：一个吃广度，一个吃深度。
